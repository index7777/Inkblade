# 墨劍訣 · 架構評估 + 分階段遷移計畫

> 目的:為「8 畫卷 + 多角色 + 技能持續擴充」的路線做好架構。
> 原則:**線上測試為主、離線雙擊為輔**;**分階段遷移、每階段可跑可回滾可驗收**、不做 big-bang 重寫。
> 撰寫日期:2026-08-11。基於當下 `inkblade.html`(5948 行)、`data/game-config.js`(1070 行)盤點。

## 一、現況盤點

### 1.1 檔案與載入
目前已經是「三檔」,不是純單檔:
- `data/game-config.js`(1070 行):技能/問道**資料** + 效果 DSL(OP_SCHEMA)+ runtime(createRunState / applyInsight / recomputeForFormation / noteKill…)。
- `data/sound-system.js`:外部音訊系統(主檔另有 `SND_LEGACY` 內聯備援,疑似重複,待釐清)。
- `inkblade.html`:HTML/CSS(前 ~857 行)+ **一個內聯 `<script>`(約 5088 行、206 個頂層函式)**。

**結論:痛點集中在那個 5088 行的內聯 `<script>`**——工具吃不到、行號漂、特例散落。

### 1.2 已經做得好的部分(可當種子)
- **技能系統資料驅動**:`game-config.js` 用「資料 + 效果 DSL」描述技能,新技能多半是加資料。這是全案最值得延用擴張的模式。
- **設定/runtime 與主檔分離**:數值、稀有度、境界門檻、問道都在 config。
- **敵人種類資料化**:`ENEMY_KINDS[]`(1409)以資料描述各敵種;精靈圖 `ENESPR` 也資料化。
- **音訊已外部化**。

### 1.3 會擋住「8 畫卷 + 多角色」的結構性問題
1. **沒有「畫卷/場景」抽象層**。目前「畫卷」只是 9:16 畫布 + **一條連續的「境」進程**:`waveDifficulty(w)` 公式 + `waveEnemyKind(w)` + 硬寫精英(第 30 境 netherSpider)+ 硬寫 BOSS(第 60 境 玄冥墨蛟)。**8 個畫卷目前不存在**——整局就是一條打到 60 境的無盡卷。要做 8 卷,需要「每卷 = 自己的波次/敵群/BOSS/背景/音樂/(可能)角色」的場景系統。
2. **BOSS 硬寫單一**:`XUANMING_CONFIG` + 約 20 個 boss 函式(bossPhase / spawnBossAttack / updateBossP1 / placeBoss…)。8 卷若各有 BOSS,照現況會把這套**複製 8 次**。需要「BOSS = 資料規格 + 共用 BOSS 引擎」。
3. **角色是三份 bespoke 程式**:HEROSPR / HEROF / HEROX 三套,靠 `meta.heroSkin` + `heroSet()` 切換,但各自有專屬繪製(drawHeroSprite / drawHeroF / drawHeroProc)。角色一多,bespoke 程式線性膨脹。需要「角色定義層(數值・sprite・專屬 hook)」。
4. **全域強耦合**:`G`(遊戲狀態)、`stat`(衍生數值)、`ctx/W/H/DPR`、`meta` 被 206 個函式直接讀寫。這是「拆檔要小心」的根源——模組化時需要一個共用的 core 狀態模組讓其他模組匯入。
5. **繪製層龐大且與全域黏死**:程序化角色/劍/紙張/HUD 全部直接讀 `stat/G/ctx`。

### 1.4 好消息:模組邊界其實已經畫好了
主檔的區塊註解已把程式分成約 25 個領域(音律、角色美術、遊戲狀態、敵人、劍/戰鬥、粒子、詞條池/runtime 橋接、升級/選卡、輸入、更新、DPS、角色繪製、劍繪製、靜態圖層、繪製、HUD、迴圈、診斷、開始/結束、暫停、轉世閣 UI、洗點、音量、商城)。**這些就是天然的模組切法**,拆檔不是從零判斷。

## 二、目標架構

### 2.1 兩條主軸
- **A. 建置 + 模組系統(Level 2)**:ES module + 一個一鍵 build(esbuild/vite)。開發跑本機 http;build 產出兩包:**線上部署包** 與 **離線自足單檔 HTML**。→ 拿回全部工具、順帶解掉 iOS 音樂(http 下音樂可走 WebAudio)。
- **B. 引擎 / 內容 分離 + 資料驅動內容**:這才是能撐 8 卷的關鍵,比拆檔更重要。

### 2.2 目標分層
```
引擎(Engine) —— 不認識「哪一卷、哪個角色」
  ├─ core        共用狀態與環境:G / stat / ctx / viewport(W,H,DPR) / RNG / 時間
  ├─ loop        遊戲迴圈、固定步進、暫停
  ├─ render      繪製管線(圖層順序、相機、紙張背景)
  ├─ input       畫線輸入
  ├─ audio       音訊(已外部化,收斂 SND_LEGACY 重複)
  ├─ save        meta 存檔 / 離線收益
  └─ scene       場景/畫卷管理器:載入一卷的資料 → 驅動波次/敵群/BOSS/背景/音樂/勝負

系統(Systems) —— 讀資料、不寫特例
  ├─ combat      飛劍・劍令・劍陣(fan/parallel/inline/merge)・命中・耐久
  ├─ intent      劍意狀態(蝕/鎮/斷)
  ├─ enemy       敵人 AI 與生成(吃 enemy/wave 資料)
  ├─ boss        共用 BOSS 引擎(吃 boss 規格)
  ├─ entities    墨獸/劍樁/粒子等實體繪製
  └─ ui          HUD / 選卡 / 暫停 / 轉世閣 / 商城

內容(Content) —— 純資料(可被非工程改)
  ├─ skills      = 現有 game-config.js(延用擴充)
  ├─ characters  角色定義:數值・sprite 組・專屬 hook id
  ├─ enemies     敵種資料(由 ENEMY_KINDS 升級)
  ├─ bosses      每卷 BOSS 規格(由 XUANMING_CONFIG 抽象)
  └─ scrolls     8 畫卷:每卷的波次曲線/敵群/精英/BOSS/背景/音樂/可用角色
```

**核心思想**:新增一卷 = 加一份 `scrolls/scroll-N` 資料 + 需要時掛少量 hook;新增角色 = 加一份 `characters/x` 資料 + sprite;**不改引擎與系統**。BOSS 從「複製 8 次程式」變「填 8 份規格」。

### 2.3 build 決策
- 目標用 **esbuild**(單一執行檔、極快、設定極少)產出兩種輸出;或 vite(dev server 體驗更好)。
- 離線需求由 **build 的「單檔內聯」產物**滿足,而不是靠「主邏輯內聯在原始碼」。→ 原始碼可以好好模組化,離線照樣拿得到。
- 只有走 ES module 才需要 build;這是為了 8 卷規模值得付的一次性成本。

## 三、分階段遷移(每階段可跑・可回滾・可驗收)

> 通則:每階段結束都要 (1) 遊戲雙擊/線上都跑得起來且行為不變(除非該階段刻意改)、(2) 抽 script `node --check`、(3) 手動實測一局 + 截圖、(4) commit 成回滾點、(5) CHANGELOG 一條。

### Stage 0 — 安全網:抽離內聯 script(Level 1)
- 把 `inkblade.html` 的內聯 `<script>` 整段搬到 `game.js`,HTML 改 `<script src="game.js">`(順序接在 config、sound 之後,與現況一致)。
- **零行為變更**,驗收標準=「跟現在一模一樣」。線上/離線都照跑。
- 產出:立刻拿回 IDE/AST/graphify/eslint、行號穩定。
- 風險:**低**(純搬移;注意載入順序與 parse-time 執行如 `resize()`)。工作量:小。

### Stage 1 — 依領域切模組(仍免 build,傳統多 `<script src>`)
- 依 1.4 的區塊把 `game.js` 切成 ~10 個檔(core / audio / enemy / combat / render / hero-art / ui / scene-lite / boss / main),用多個 `<script src>` 依序載入。仍是全域共用(尚未 import/export)。
- 目的:先把**邊界畫出來、把跨檔依賴看清楚**,為 Stage 2 的 ES module 化鋪路。
- 風險:**低—中**(要理順全域讀寫順序)。工作量:中。

### Stage 2 — ES module + esbuild(Level 2 地基)
- 導入 esbuild;把 Stage 1 的檔轉成 `import/export`。先抽出 **core 模組**(G / stat / ctx / viewport / rng),其他模組明確匯入,消除隱性全域。
- dev 跑本機 http;build 產出「線上包 + 離線單檔」。
- 此後 **iOS 音樂可修**(音樂改走 WebAudio)。
- 風險:**中**(全域→匯入的機械但廣泛改動)。工作量:中—大。

### Stage 3 — 內容資料化 + 場景管理器(最關鍵)
- 建 `scene` 管理器:一局 = 載入某卷資料 → 驅動波次/敵群/精英/BOSS/背景/音樂/勝負。
- 把現況這條「打到 60 境」的進程,原樣搬成 **scroll-1 的資料**(waveDifficulty/waveEnemyKind/精英@30/boss@60 → 資料欄位)。**遊戲行為不變,只是改由資料描述**。
- 敵種 `ENEMY_KINDS` → `content/enemies`;角色 HEROSPR/F/X → `content/characters`(+ 專屬 hook id)。
- 風險:**中**(抽象化容易漏行為,需逐項對照)。工作量:大。**回滾點務必密**。

### Stage 4 — BOSS 引擎化
- 把 `XUANMING_CONFIG` + ~20 boss 函式抽象成「BOSS 規格(相位/招式/位移/彈幕表)+ 共用 BOSS runtime」。玄冥墨蛟成為第一份 boss 規格。
- 之後每卷 BOSS = 一份規格 + 需要時少量招式 hook。
- 風險:**中—高**(BOSS 邏輯最密)。工作量:大。可延後到需要第二個 BOSS 時再做。

### Stage 5 — 擴內容:8 畫卷 + 多角色
- 依 scroll/character 資料格式,逐卷、逐角色新增。此時新增內容**不動引擎/系統**。
- 風險:**低**(靠前面投資把風險前移了)。工作量:隨內容量,但邊際成本低。

## 四、與現有功能路線的排序建議

現有待辦:轉世閣前置 → 真意主動四式(耦合最大)。架構遷移與它們的關係:

- **真意主動四式是「耦合最大」的功能**——正是最會踩「漏改呼叫點」的地方(我們已在引鋒、定鋒踩過)。**強烈建議它在模組化之後、工具查得動的碼上做。**

**建議總順序:**
1. **Stage 0(抽離)** — 現在就做,趁卡片剛完工、樹乾淨,零行為變更、低風險。
2. **Stage 1—2(模組化 + esbuild)** — 一次把地基打好(這就是你要的「痛一次」的核心)。
3. **轉世閣前置** — 在新結構上做,當暖身。
4. **真意主動四式** — 在乾淨模組上做,耦合風險最低;一筆開天(聚鋒極致版)、卡片文字併此輪。
5. **Stage 3(內容資料化 + 場景)** — 接著做,把「現況」變成 scroll-1。
6. **Stage 4 BOSS 引擎** — 需要第二個 BOSS 時做。
7. **Stage 5** — 開始量產 8 卷 + 多角色。

> 若想更保守:可把 Stage 3 場景化插在真意之前(讓真意直接在資料化世界裡做)。取捨:場景化較大、先做會延後真意。我的傾向是**先地基(0–2)、再真意、再場景**,因為真意的痛主要來自「碼難查」,Stage 0–2 就解掉了。

## 五、風險與成本總表

| 階段 | 風險 | 工作量 | 可回滾 | 主要價值 |
|---|---|---|---|---|
| 0 抽離 | 低 | 小 | 極易 | 立刻拿回工具、行號穩 |
| 1 切模組 | 低—中 | 中 | 易 | 邊界清晰、依賴可視 |
| 2 ESM+build | 中 | 中—大 | 中 | 真模組化、解 iOS 音樂 |
| 3 內容資料化+場景 | 中 | 大 | 需密回滾點 | 8 卷的地基 |
| 4 BOSS 引擎 | 中—高 | 大 | 中 | BOSS 從複製變填表 |
| 5 擴內容 | 低 | 隨量 | 易 | 邊際成本低 |

**共同風險與對策**
- 回歸(最大風險):每階段零行為變更、逐項對照、密 commit、`node --check` + 實測 + 截圖。高風險階段(3、4)用子代理獨立驗證。
- 兩機協作:模組檔數變多、又多了 build,`SYNC.bat`/git 流程要先講好(誰動哪個模組、build 產物要不要進版控)。動大手術前兩台先 pull/push 對齊。
- 「痛一次」但不「一次痛完」:0→2 是一個可停的完整里程碑(地基好了、真意能舒服做);3→5 可依內容節奏再推進。

## 六、建議的第一步

- 先做 **Stage 0(抽離內聯 script → `game.js`)**:零行為變更、低風險、立刻見效,也是後續一切的前置。
- 我可以接著出 **Stage 1—2 的細部拆檔清單**(每個模組含哪些函式、跨檔依賴、core 要抽哪些全域),讓「痛一次」是照圖施工而非邊做邊想。

> 一句話:Level 1(Stage 0)只是止痛;真正撐得起 8 卷的是 **模組化地基(0–2)+ 內容資料化與場景/BOSS 引擎(3–4)**。分階段做、每步可回滾,就能「痛一次」而不冒 big-bang 的險。
